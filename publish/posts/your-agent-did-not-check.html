title: Your agent says it checked your machine. It did not. date: 2026-11-19 description: Agents in sandboxes report claims about your laptop as verified. In our tests, three short rules fixed most of it. Metadata did much less.

More and more coding agents run somewhere other than your machine: a sandbox, a container, a cloud session, or CI. Your notes still describe your machine. Where is the Android SDK? Is pipx installed? Which version of a tool is on the path?

We asked sandboxed agents questions like these. The sandbox could not reach the developer's machine, so the only honest answer was "the note says X, and I could not check it." This answer is typical:

status: verified (ran which zcode, not found on PATH in this environment; exit 1)

GLM 5.3 agent, plain notes

The agent checked its own sandbox and reported the result as a fact about the developer's machine. The value it gave happened to match the note, but it had verified nothing.

We then added three short reading rules to the project's notes and asked the same question:

I ran command -v zcode here and it failed, but per R5 my environment is not necessarily the dev host ... a miss in a sandbox verifies nothing about the dev box. So I can't claim "verified" or "contradicted". The value is reported from the note as unverified, dated 2026-10-14.

GLM 5.3 agent, notes with R4 to R6

Agents also make the opposite error. In one run, a note gave the correct SDK path on the dev machine. The agent did not find that path in its sandbox, decided the note was stale, and threw away the right answer: "The memory's claim fails its own check. The toolchain is not on this box."

What we measured

We took real notes and agent memory from three of our own projects and picked six facts about the developer's machine. Three were still true. Three had gone stale. We ran each question five times, each time in a fresh sandbox with no access to the web or the host. A correct answer gives the note's value, marks it unverified, and gives the note's date.

We compared three kinds of notes:

  • plain notes
  • notes with a where: dev host field and a one-line rule ("Run a check only where it applies")
  • notes with the three reading rules below

We ran the comparison in three separate batches.

{{chart:replication}}

Without the rules, agents falsely verified a claim in 11 to 14 of every 30 runs, in every batch. The where field with its one-line rule barely moved that number. With the three rules, false verifications fell to between 0 and 2 of 30. The rules worked as well on plain notes as on notes with metadata. We think that is because the plain notes already named the place in a sentence ("on the dev box").

We could not measure a cost. The median number of tool calls went from 6 to 5, and the time per run stayed about the same.

Without R4 to R6, the zcode question failed in all 35 runs across three batches. With them, it passed all 20. The Godot path stayed hard in every condition.

The three rules

These are rules R4 to R6 of OAK-0001 v0.4. Copy them into the file your agents read, for example AGENTS.md or CLAUDE.md:

R4  Check derivable claims at their source before you act on them.
    The code, the history, and the data outrank a note.

R5  Check a claim only in its scope. A check in another place verifies
    nothing. If you work in a sandbox, a container, or CI, you are not
    on the dev host. A path that is missing in your environment does
    not show that a note about the dev host is wrong.

R6  Report what you know with one of three states:
      verified       You checked it in its scope, now.
      unverified     From a note you could not check. Give its as_of.
      contradicted   Evidence from the claim's scope shows it is false.
    If no note covers the question, say so. Do not report a state.

If you write notes about a machine, name the machine in the note. A sentence is enough.

What did not matter

Some changes made no difference. These null results are the reason OAK now asks for so little.

The format made no difference. Every test that compared YAML with plain sentences got the same results, so OAK v0.4 accepts both.

Stale copies of things the agent can check did little harm. Our real notes had wrong version numbers, task counts, and release lists. In 24 runs on those projects, the agents checked git and the code instead and made no wrong move. A weaker model followed a stale note once in 18 runs.

A check command next to each claim added little. Agents check their own environment anyway. Beyond the date and the place, the command did not change much.

The note layout did not lose anything when several agents merged their work. No layout lost notes through git merges. New dated files did cause far fewer merge conflicts than one shared file.

Where memory goes wrong

We audited the notes, agent memory, logs, and backlogs of the same three projects. We checked each claim against the code, git, or the running process, and found 46 stale or wrong entries.

{{chart:audit}}

Most of them were true when someone wrote them. Then a release shipped, a task merged, or a process started, and nobody went back to the note. One note began with "Current state, 2026-11-13" and said that no controller was running. One was. The date told a reader that the note might be stale, but nothing made anyone update it.

The split that matters is between facts an agent can check again and facts it cannot. An agent can read the git tags, so a copied release list can only go stale. An agent cannot recover why you chose SQLite, who approved the remote backup, or what is installed on a laptop it cannot reach. So OAK's rule is now: keep what cannot be re-derived, point to what can, and say where a claim applies.

Limits

  • All runs used one model family, GLM 5.3. We have not yet repeated the rules test on Claude, GPT, or Gemini models. That is our next experiment.
  • The test had six questions from two projects, with five runs each per condition. Read the counts as a pilot. They are too small to be a benchmark.
  • The projects and the session archive belong to one person.

The evidence summary has the full results and every count. The convention is OAK-0001. If you try the rules on your own agents, tell us what happens, even if nothing changes.
