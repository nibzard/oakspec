OAK-0001 evidence                                              2026-11-24
What the tests behind OAK-0001 v0.4 and v0.5 found, including null results
https://oakspec.dev/evidence.txt

SCOPE

  All tests below used one person's projects and agent sessions. Most
  agent runs used one model family (GLM 5.3). Each test is a pilot. Read
  the counts as descriptions, not as proof. Agent runs used Pi with tools
  in a fresh Gondolin guest and no guest web access, unless noted.


1. WHAT FAILS IN REAL MEMORY

  Audit of three real projects (papercut, looper, barista), 2026-11-18.
  46 verified defects in notes, agent memory, logs, and backlogs.

  - Most were true when written. Nobody revisited them after a later
    event: a release, a merged task, a controller start.
  - A dated header ("Current state, 2026-11-13") was still wrong.
    A date shows staleness. It does not cause an update.
  - Writes got lost: notes stayed in task branches that never merged.

  Mining of the author's archive of agent sessions: 12 clear memory
  failures in 700 screened user corrections. Most were lost decisions or
  stale tool workflows. Most memory rot is silent.


2. EARLIER COMPARISONS (OAK V0.2 AND V0.3)

  Papercut repository questions, 120 runs: accuracy 0.918 with OAK,
  0.915 without. 24% fewer tool calls with OAK, not significant. The
  study changed metadata, an index, and curated notes together.

  Metadata versus equivalent prose, 24 sessions, and a 60-session
  longitudinal pilot: both conditions passed every configuration check.
  Tool calls were similar. The tasks were too easy to separate them.


3. STALE NOTES ON REAL REPOSITORIES (E1)

  48 runs on real repository snapshots, four conditions: notes as they
  were, no notes, notes with YAML dates and checks, and the same facts in
  sentences.

  - Stale notes about derivable state (versions, task counts, whether a
    task landed) caused no wrong actions in 24 runs. Agents checked git,
    code, and data.
  - A weaker model (GLM 5.3 Flash) followed a stale note in 1 of 18 runs.
  - Notes changed the outcome only for facts the agent could not check,
    for example tool paths on the developer's machine.
  - YAML and sentences gave the same results.


4. CLAIMS ABOUT ANOTHER MACHINE (E1B AND V0.4 CHECKS)

  Six questions about the developer's machine, asked of an agent in a
  sandbox that cannot reach it. Correct: report the note's value as
  unverified, with its date.

                                   correct   false verify
  Notes as they were                12-15/30     12-14
  Notes with a where field          18-19/30     11
  Plain notes + rules R4-R6         27/30         2
  Notes with where + rules R4-R6    28/30        0-2

  The rows come from four batches. Each batch compared its conditions
  under one seed. Not every batch ran every condition: E1b ran four
  forms of notes without the rules (two more not shown here: 14 and 11
  false verifications), and the candidate check ran only the rules.
  Without the rules, agents often ran a check in their own sandbox and
  called a claim about the other machine verified. The rules fixed this
  on plain notes that named the place in a sentence.

  The zcode question: 35 of 35 runs without the rules were false
  verifications, and 20 of 20 runs with the rules were correct.

  Caveat: every task prompt defined "verified" as "you checked the
  values in your environment". That wording invites the error in every
  condition. Rule R6 replaces it with "checked in its scope".


5. SEVERAL AGENTS AT ONCE (E3)

  36 rounds. Three agents worked in separate git worktrees, then merged.

                               lost records   conflicts   round time
  One shared NOTES.md                0            24          107 s
  Topic files + index (v0.3)         0            24          230 s
  New dated record files             0             6           52 s

  No layout lost records through git merges. New record files cost the
  least. Not tested: branches that never merge, and tools that overwrite
  files outside git.


6. V0.4 SETUP AND EDGE CASES

  Setup from the v0.4 text on a real project, 3 runs: no note content
  lost, no invented dates. One run reported edits that its files did not
  contain. The self-check now reports from the files.

  Deletion, a withdrawn approval, and an injected instruction: 8 of 9
  runs passed with OAK, 9 of 9 without. These cases were too easy to
  separate the conditions.


7. V0.5 COLD-START, PROBE, RECEIPT, AND MERGE CHECKS (2026-11-24)

  114 Gondolin VM runs across two batches (GLM 5.3, no guest web access,
  host ~/.agents/AGENTS.md blocked):

  Cold-start setup -> offline audit (neutral prompt, no definition of
  "verified", two host-scope questions per run):

                                false verify   false contradict   tokens
  Plain setup + AGENTS.md           3/6              1/6          16,172
  OAK v0.4 setup (URL pointer)      5/6              1/6          14,517
  OAK v0.5 initial                  1/6              1/6          12,614
  OAK v0.5 refined (sandbox R5)    0/10             0/10          12,204

  v0.4's URL-only pointer gave no protection offline because the reader
  could not fetch the spec. Telling readers to treat unconfirmed
  workspaces as sandboxes (R5) eliminated both false verifications and
  false contradictions.

  State versus intent and forbidden probes: all arms passed unapplied
  approval and stale-constant checks (9/9 each). On an unapplied
  revocation, 2 of 3 initial v0.5 runs invoked the disabled production
  script after editing config "to confirm it was disabled." Adding R1's
  rule against probing unapproved or revoked targets cut probes to 0/5.

  Handoff receipts (W9, R9): when a handoff message already listed a path
  and sha256 digest, readers caught missing files and corrupted drafts
  with and without R9 (9/9 each). In an end-to-end two-session handoff,
  3 of 3 OAK v0.5 writers emitted sha256 digests in HANDOFF.md versus 0
  of 3 plain writers; both arms blocked a contradictory draft overwrite
  (3/3) when HANDOFF.md also stated the decision in prose.

  Three-way parallel merges (2 rounds per layout, 2 merges per round):

                                conflicts   resolver time   reader recall
  One shared NOTES.md              4/4          81.0 s        6/6 (2/2)
  v0.4 per-file index.md           4/4          87.3 s        5/6 (1/2)
  v0.5 folder-linked index.md      0/4           0.0 s        6/6 (2/2)

  In v0.4 round 1, an index.md conflict resolver paraphrased "once the
  DPA was signed" to "once the DPA is signed," causing the reader to
  leave an approved flag false. Linking records/ as a folder avoided
  every conflict.


8. WHAT THIS MEANS FOR OAK

  - Short reading rules changed agent behavior more than any metadata,
    but only if setup puts them in local context (AGENTS.md) for offline
    sessions.
  - Verification rules need two guardrails: treat unconfirmed workspaces
    as sandboxes (R5), and never probe revoked targets to test failure
    (R1).
  - Linking folders rather than individual records from index.md prevents
    both merge conflicts and resolver paraphrasing errors.
  - Copied derivable state is waste, not the main danger, for capable
    agents. Notes earn their place for facts nobody can re-derive.
  - YAML is for deterministic tools and link checks, not LLM reading.

  Open: other model families, long-horizon consolidation with renames,
  and parameter-only overwrites where HANDOFF.md does not repeat prose.

END OF EVIDENCE
