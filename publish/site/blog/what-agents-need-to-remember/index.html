What agents need to remember

OAK gives project knowledge a shared home. Our handoff tests helped us decide what belongs in the spec and what agents can work out for themselves.

  1. Give unique knowledge a home. Save decisions and context a future agent cannot recover. Point to the source for facts it can check.
  2. Make the meaning clear. Say who supplied the information, where it applies, and which earlier decision it replaces, if any.
  3. Make knowledge easy to find and update. Give readers a short index and links that explain what they lead to. When agents work in parallel, let each add a separate record.
  4. Confirm receipt. Check that the next reader can reach the intended version in the shared location.

These are the ideas behind Open Agent Knowledge. To try it, give your agent the single-file OAK specification and ask it to set up or maintain your project's knowledge. The file includes setup steps for projects that already have notes.

What belongs in that shared home?

A project specification says what to make. The repository and its live systems show what exists. The context around that work can be harder to recover. Why did the editor move the release? Who approved the exception? Did it apply to a preview or to public publication?

Say an editor approves a preview before anyone updates the publishing settings. That distinction tripped up an agent in a simulated handoff about a staging export. It treated the disabled setting as evidence that approval had ended. The next agent left the approved work undone. The setting was accurate. The note's account of the decision was wrong.

I'd record the approval, who gave it, and where it applies. If the editor withdraws it, I'd keep the original record, link the withdrawal to it, and update the note that tells the next reader what applies now. For the current publishing state, I'd point the reader to the configuration. The same distinction matters when a note describes a remote machine. A check on your laptop tells you about your laptop.

What the tests persuaded me to keep

Agents answered repository questions at about the same rate with and without OAK. When they could check code or Git history, they usually did. Notes mattered more when the owner's decision was available only through the handoff. Plain Markdown also carried the approval through once we gave decisions and observed settings separate places.

Make knowledge easy to find and update

In the parallel-writing pilot, separate dated records produced 6 merge conflicts. One shared notes file produced 24. Separate plain Markdown and OAK records both merged cleanly in a follow-up. When agents work in parallel, I'd give each decision its own file and keep its scope and reason with it. The pilot compared layouts. File length, folder depth, and wiki-link syntax are still open questions. Pilot evidence

Start at knowledge/index.md. Keep it short by linking to groups of records. A writer can then add a record without editing the index on every branch. Add folders when the notes group naturally by project or topic. Put the relationship in the link text. For example, write [Replaces the original preview approval](records/preview-approval.md). That tells the next reader why the original matters.

Confirm receipt

The delivery test made the last rule concrete. We simulated a decision stuck in an unmerged worktree and a stale import that overwrote a newer decision. When the host checked the recipient's copy and restored the intended file, the next agent used the current approval. Without that check, it followed the old hold. Both note formats behaved the same. The test assumed the host knew where to look and still had the sender's copy.

What should get easier as models improve?

My reading of Rich Sutton's Bitter Lesson is that we should expect models to get better at finding evidence and working through inconsistencies. Give them a predictable place to start and room to choose how they search and reason. Preserve the facts and relationships they would otherwise have to guess. A smarter agent may need less help reading a note. It still needs the editor's decision to reach its worktree. The Bitter Lesson

That's the job I want one specification file to do. It gives agents shared rules for keeping, finding, and handing off decisions. For the next version, I'd test whether a stable record identifier helps two independent tools find the same decision after a rename or transfer. That would give any extra structure a clear reason to be there.
