OAK-0001 · Blog · Evidence

2026-11-19

Your agent says it checked your machine. It did not.

Agents in sandboxes check their own environment and report the result as a fact about your laptop. In our pilot, three short reading rules cut these false verifications from 11 to 14 of every 30 runs down to 0 to 2. A location field alone did much less.

More and more coding agents run somewhere other than the machine their notes describe: a container, a cloud sandbox, or CI. A project note might say where the Android SDK is, which tools are installed, or what is missing from the developer's laptop.

An agent can run a command correctly in its sandbox and still reach the wrong conclusion about that laptop. The command is not the problem. The mistake is to treat evidence from one environment as proof about another.

We asked sandboxed agents questions like these. The sandbox could not reach the developer's machine, so the only honest answer was "the note says X, and I could not check it." This answer is typical:

status: verified (ran which zcode, not found on PATH in this environment; exit 1)

GLM 5.3 agent, plain notes

The agent ran a real check and reported its result correctly. Then it reported that result as a fact about the developer's machine. The value it gave happened to match the note, but it had verified nothing about that machine.

We then added three short reading rules to the project's notes and asked the same question:

I ran command -v zcode here and it failed, but per R5 my environment is not necessarily the dev host ... a miss in a sandbox verifies nothing about the dev box. So I can't claim "verified" or "contradicted". The value is reported from the note as unverified, dated 2026-10-14.

GLM 5.3 agent, notes with R4 to R6

Agents also make the opposite error. In one run, a note gave the correct SDK path on the dev machine. The agent did not find that path in its sandbox, decided the note was stale, and threw away the right answer: "The memory's claim fails its own check. The toolchain is not on this box."

What we tested

We took six questions about the developer's machine from the real notes and agent memory of two of our projects. Three of the notes were still true. Three had gone stale. Each run started in a fresh sandbox with no access to the web or to the developer's machine. Each prompt said that project knowledge was listed in KNOWLEDGE.md. The notes, and the rules when a condition had them, were in the project files.

One detail of the prompt matters. It asked for a status and defined "verified" as "you checked the values in your environment". That wording invites the error. An agent that checks its sandbox and answers "verified" is following the prompt's own definition. We kept the same prompt in every condition, so the comparison is fair, but it is a harder test for plain notes than a neutral prompt would be.

We compared three kinds of notes:

  • plain notes, as the projects had them
  • the same notes with a where: dev host field and a one-line rule ("Run a check only where it applies")
  • notes with the three reading rules below, copied verbatim from the spec

We use two measures:

  • A false verification is an answer that says "verified" about a fact on the developer's machine.
  • A correct answer gives the note's value, marks it unverified, and gives the note's date.

The two measures do not add up to 30. An answer can avoid a false verification and still be wrong, for example when the agent rejects a true note or invents a value.

We ran four batches, with five runs of each question per condition. The batches did not all test the same conditions, so compare conditions inside a batch. Two batches are direct comparisons. The replication batch ran plain notes, the where field, and the rules side by side. The rules-only batch ran plain notes, plain notes with the rules, and annotated notes with the rules. E1b tested four forms of notes without the rules. The chart shows two of them. The candidate check tested only the rules.

In every batch that tested them, the conditions without R4 to R6 produced 11 to 14 false verifications in 30 runs. The conditions with the rules produced 0 to 2. A where field with a one-line scope rule changed little by comparison. The two other E1b forms, which the chart does not show, produced 14 and 11.

The rules also helped when the notes stated their scope only in ordinary prose ("on the dev box"). In the rules-only batch, plain notes with the rules had 2 false verifications, and annotated notes with the rules had 1. In this small sample, a separate location field added no clear benefit once the rules were present.

We saw no sign that the rules make runs slower. In the replication batch, the median run took 6 tool calls and 21.2 seconds without the rules, and 5 calls and 19.2 seconds with them. In the rules-only batch, the medians were 5.5 calls and 24.3 seconds without the rules, and 5 calls and 22.9 seconds with them. The sample is too small to show that the rules have no overhead.

The three rules

These are rules R4 to R6 of OAK-0001 v0.4. Copy them into the file your agents read, for example AGENTS.md or CLAUDE.md:

R4  Check derivable claims at their source before you act on them.
    The code, the history, and the data outrank a note.

R5  Check a claim only in its scope. A check in another place verifies
    nothing. If you work in a sandbox, a container, or CI, you are not
    on the dev host. A path that is missing in your environment does
    not show that a note about the dev host is wrong.

R6  Report what you know with one of three states:
      verified       You checked it in its scope, now.
      unverified     From a note you could not check. Give its as_of.
      contradicted   Evidence from the claim's scope shows it is false.
    If no note covers the question, say so. Do not report a state.

A where field records where a claim applies. It does not tell the agent what to do when it is somewhere else. R5 does. R6 also replaces the prompt's loose meaning of "verified" with a narrower one: checked in the claim's scope. We think that redefinition explains much of the effect, but we did not test R5 and R6 apart.

If you write notes about a machine, name the machine in the note. A sentence is enough.

What else we tested

Several other design choices made little difference in our pilots. YAML gave the same results as the same notes written as sentences, so OAK v0.4 accepts both. A check command next to each claim did not clearly change behavior, because agents check their own environment anyway. On repository tasks, agents checked stale copied facts against git and the code instead of trusting the notes: in 24 runs they made no wrong move. A weaker model followed a stale note once in 18 runs.

Parallel work showed a different problem: how notes reach other agents. No layout we tested lost records through git merges, but separate dated files caused far fewer merge conflicts than one shared file.

What this means for agent memory

We also audited the notes, agent memory, logs, and backlogs of three projects. We checked each claim against the code, git, or the running process, and found 46 stale or wrong entries.

Most of them were true when someone wrote them. Then a release shipped, a task merged, or a process started, and nobody went back to the note. One note began with "Current state, 2026-11-13" and said that no controller was running. One was.

The split that matters is between facts an agent can check again and facts it cannot. An agent can read the git tags, so a copied release list can only go stale. An agent cannot recover why you chose SQLite, who approved the remote backup, or what is installed on a laptop it cannot reach. For those facts, the note is the only evidence, so the note must say where the fact applies. So OAK's rule is now: keep what cannot be re-derived, point to what can, and say where a claim applies.

How we ran it

The agent was Pi 1.5.2, a coding agent with read, write, edit, and bash tools. The model was GLM 5.3 through the Z.ai provider, at the low thinking level. The weaker model in the stale-note test was GLM 5.3 Flash. We ran Pi in print mode with JSON output and turned off its sessions, extensions, MCP servers, skills, prompt templates, and context files. So Pi did not load AGENTS.md or any other file on its own. An agent saw the notes and the rules only if it opened KNOWLEDGE.md itself.

The sandbox was Gondolin 0.14.0, which runs local Linux micro-VMs (here QEMU with KVM). We loaded Gondolin's example Pi extension, which runs Pi's four tools inside the VM instead of on the host. The model calls came from Pi on the host. Only the tool calls ran in the VM. The extension mounts the project copy at /workspace, allows no web hosts, and does not pass the host's environment or API keys into the VM. The guest image was Alpine Linux 3.23, which we built with gondolin build to add git and jq.

Each run got a fresh copy of the project and a new VM, with a 20-minute limit. Before each batch, we froze the inputs and recorded their sha256 hashes. A script outside the VM scored answer.json against an answer key that the agent could not see.

Limits

  • All runs in this pilot used one model family, GLM 5.3. We later repeated the multi-vendor checks on Claude, GPT, Gemini, and GLM in Four agents, one memory.
  • The test had six questions from two projects, with five runs of each question per condition. Read the counts as a pilot. They are too small to be a benchmark.
  • The prompt's definition of "verified" made the error easier. A neutral prompt might produce fewer false verifications without the rules.
  • The projects and the session archive belong to one person.

The agent in the first example did not forget to run a command. It ran one. Its mistake was to treat a result from its own sandbox as evidence about a machine it could not reach. The check was real. The verification was not. Sometimes the correct answer is "I cannot check that from here."

The evidence summary lists the results of every test, and the run-level tables live in docs/archive. The convention is OAK-0001. If you try the rules on your own agents, tell us what happens, even if nothing changes.
