OAK-0001 · Blog · Evidence

2026-11-19

Your agent says it checked your machine. It did not.

Agents in sandboxes report claims about your laptop as verified. Three short rules fixed most of it in our tests. Metadata did much less.

Coding agents increasingly work away from your machine: in a sandbox, a container, a cloud session, or CI. Your notes describe your machine. Where is the Android SDK? Is pipx installed? Which version of a tool is on the path?

We asked agents in a sandbox about facts like these. The sandbox could not reach the developer's machine, so the only honest answer was "the note says X, and I could not check it." Here is a typical answer:

status: verified (ran which zcode, not found on PATH in this environment; exit 1)

GLM 5.3 agent, plain notes

The agent checked its own sandbox and reported the result as a fact about the developer's machine. The value happened to match the note. The claim that it was verified was false.

Here is the same question after we added three short reading rules to the project's notes:

I ran command -v zcode here and it failed, but per R5 my environment is not necessarily the dev host ... a miss in a sandbox verifies nothing about the dev box. So I can't claim "verified" or "contradicted". The value is reported from the note as unverified, dated 2026-10-14.

GLM 5.3 agent, notes with R4 to R6

The opposite error also happens. In one run, a note correctly gave the SDK path on the dev machine. The agent could not find the path in its sandbox, decided that the note was stale, and discarded the right answer: "The memory's claim fails its own check. The toolchain is not on this box."

What we measured

We took real notes and agent memory from three of our own projects. We picked six facts about the developer's machine. Three were still true, and three had gone stale. Each question ran five times in a fresh sandbox, with no access to the web or the host. A correct answer reports the note's value as unverified, with the note's date.

We compared plain notes, notes with a where: dev host field and a one-line rule ("Run a check only where it applies"), and notes with the three reading rules below. We repeated the comparison in three separate batches.

Without the rules, agents falsely verified a claim in 11 to 14 of every 30 runs, in every batch. The where field with a one-line rule barely changed that. With the three rules, false verifications fell to between 0 and 2 of 30. The rules worked as well on plain notes as on notes with metadata, because the plain notes already named the place in a sentence ("on the dev box").

The rules cost nothing measurable. The median number of tool calls went from 6 to 5, and the time per run stayed about the same.

Per question, the change is easy to see. This is one batch, run under one seed:

The zcode question failed in all 35 runs without R4 to R6, across three batches. With them, it passed all 20. One question, the Godot path, stayed hard in every condition.

The three rules

These are rules R4 to R6 of OAK-0001 v0.4. Copy them into the file your agents read, for example AGENTS.md or CLAUDE.md:

R4  Check derivable claims at their source before you act on them.
    The code, the history, and the data outrank a note.

R5  Check a claim only in its scope. A check in another place verifies
    nothing. If you work in a sandbox, a container, or CI, you are not
    on the dev host. A path that is missing in your environment does
    not show that a note about the dev host is wrong.

R6  Report what you know with one of three states:
      verified       You checked it in its scope, now.
      unverified     From a note you could not check. Give its as_of.
      contradicted   Evidence from the claim's scope shows it is false.
    If no note covers the question, say so. Do not report a state.

If you write notes about a machine, name the machine in the note. A sentence is enough.

What did not matter

We publish the null results too, because they explain why OAK now asks for so little.

  • YAML versus plain sentences. Every test that compared them found the same results. OAK v0.4 accepts both.
  • Stale copies of things the agent can check. Our real notes contained wrong version numbers, task counts, and release lists. In 24 runs on those projects, the agents checked git and the code instead and made no wrong move. A weaker model followed a stale note once in 18 runs.
  • A check command next to each claim. Agents check their own environment anyway. The command added little beyond a date and a place.
  • The note layout, when several agents merge their work. No layout lost notes through git merges. New dated files caused far fewer merge conflicts than one shared file.

Where memory actually goes wrong

We audited the notes, agent memory, logs, and backlogs of the same three projects and checked each claim against the code, git, or the running process. We found 46 stale or wrong entries.

Most were true when someone wrote them. Then a release shipped, a task merged, or a process started, and nobody went back. One note began with "Current state, 2026-11-13" and said that no controller was running while one was. A date tells you that a note might be stale. It does not make anyone update it.

The useful split is between facts an agent can check again and facts it cannot. An agent can read the git tags, so a copied release list only goes stale. An agent cannot recover why you chose SQLite, who approved the remote backup, or what is installed on a laptop it cannot reach. OAK's rule is now: keep what cannot be re-derived, point to what can, and say where a claim applies.

Limits

  • All runs used one model family, GLM 5.3. We have not yet repeated the rules test on Claude, GPT, or Gemini models. That is the next experiment.
  • Six questions, from two projects, with five runs each per condition. Treat the counts as a pilot, not a benchmark.
  • The projects and the session archive belong to one person.

The full results, with every count, are in the evidence summary. The convention is OAK-0001. If you try the rules on your own agents, we would like to know what happens, including if nothing changes.
